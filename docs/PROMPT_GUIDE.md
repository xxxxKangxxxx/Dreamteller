## Gemini API 호출 기본 패턴

```typescript
// server/src/services/geminiService.ts
import { GoogleGenerativeAI } from '@google/generative-ai'

const genAI = new GoogleGenerativeAI(process.env.GEMINI_API_KEY!)
const model = genAI.getGenerativeModel({ model: 'gemini-2.5-flash' })

// 일반 텍스트 생성 (해몽, 요약 등)
async function generate(systemPrompt: string, userPrompt: string): Promise<string> {
  const result = await model.generateContent({
    systemInstruction: systemPrompt,
    contents: [{ role: 'user', parts: [{ text: userPrompt }] }]
  })
  return result.response.text()
}

// 대화형 멀티턴 (꿈 기록 대화용)
function startChat(systemPrompt: string, history: { role: string; parts: { text: string }[] }[]) {
  return model.startChat({ systemInstruction: systemPrompt, history })
}
```

## 1. 대화형 꿈 기록 AI — 슬롯 채우기(slot filling) 방식

> **2026-08-16 전면 개편.** 이전 구조는 `step`이 **순수한 턴 카운터**여서 답변 내용과 무관하게 장소→인물→사건→감정을 기계적으로 물었다.
> 그래서 사용자가 첫 답변에 다 말해도 **이미 답한 것을 또 묻는** 문제가 있었다.
> 이제 **"몇 번 주고받았는가"가 아니라 "필요한 정보가 다 모였는가"** 로 진행을 판정한다.

### 수집 슬롯 (4개) — 이게 대화 종료 조건

| 슬롯 | 내용 | 비고 |
|---|---|---|
| `place` | 꿈의 장소·배경 | |
| `people` | 등장인물 | **'혼자였다'도 유효한 값** |
| `event` | 핵심 사건·장면 | |
| `emotion` | 꿈에서 느낀 감정 | |

4개가 전부 채워지면 `complete: true` → 줄거리·해몽 단계로 넘어간다.
**"기억이 안 나"도 채워진 것으로 간주**한다(값 `"기억나지 않음"`) — 안 그러면 영원히 되묻게 된다.

### 설계 원칙

- **판정을 별도 호출로 분리하지 않는다.** 답변과 슬롯 상태를 **한 번의 호출에서 JSON으로 함께** 받는다. 별도 추출 호출을 두면 턴당 Gemini 왕복이 2배가 되는데, 대화는 이미 꿈 1건 비용의 약 32%다(`IMPROVEMENTS.md` 1-1a).
- 출력 토큰은 조금 늘지만 **턴 수가 5 → 2~3으로 줄어 대화 비용은 오히려 감소**할 것으로 예상.
- 서버는 매 턴 `messages` 전체를 받으므로 **슬롯 상태를 저장할 필요가 없다.** 모델이 매번 전체 대화를 다시 읽고 재판정한다(stateless 유지).

### 시스템 프롬프트
```
당신은 드림텔러의 꿈 기록 도우미 'Luna'입니다.

역할:
- 사용자가 아침에 기억하는 꿈을 편하게 이야기할 수 있도록 대화로 이끌어주세요.
- 전문적이거나 딱딱한 말투가 아닌, 친한 친구처럼 자연스럽고 부드러운 말투를 사용하세요.
- 이모지나 이모티콘은 사용하지 마세요. 담백하고 깔끔한 문장으로만 대화하세요.

수집할 정보(슬롯) — 아래 4가지가 모두 채워지면 대화를 끝냅니다:
- place: 꿈의 장소나 배경
- people: 등장인물 (혼자였다면 '혼자'도 유효한 답입니다)
- event: 핵심 사건이나 장면
- emotion: 꿈에서 느낀 감정

대화 규칙:
1. 매 턴마다 지금까지의 대화 전체를 다시 읽고, 각 슬롯이 이미 채워졌는지 판정하세요.
   사용자가 한 번의 답변에서 여러 슬롯을 동시에 말했다면 그것을 모두 인정하세요.
2. 이미 채워진 슬롯은 절대 다시 묻지 마세요.
   사용자가 방금 말한 내용을 되묻는 것은 가장 나쁜 경험입니다.
3. 아직 비어 있는 슬롯 중 하나만 골라 질문하세요. 한 번에 하나의 질문만 합니다.
4. 사용자가 "기억이 안 나", "모르겠어"라고 하면 그 슬롯은 "기억나지 않음"으로
   채워진 것으로 간주하고 다시 묻지 마세요.
5. 슬롯이 모두 채워지면 새 질문 없이 짧고 따뜻하게 마무리하세요.

응답 언어: 한국어
```

### 출력 형식 (구조화 출력 — `response_mime_type="application/json"`)
```json
{
  "reply": "사용자에게 보여줄 문장 (빈 슬롯에 대한 질문 하나, 또는 마무리 인사)",
  "slots": {
    "place":   "채워졌으면 내용 요약, 아직이면 null",
    "people":  "...",
    "event":   "...",
    "emotion": "..."
  },
  "complete": false
}
```
- `complete`는 **`slots` 4개가 모두 null이 아닐 때 true**. 모델 판단과 서버 계산이 어긋나면 **서버의 슬롯 계산을 신뢰**한다(모델이 `complete`만 잘못 뱉는 사고 방지).
- 해몽 생성(v2)과 동일한 구조화 출력 패턴. 파싱 실패 시 폴백은 §5 참조.

### 첫 질문 — 개방형 (중요)
```javascript
// 이전: 장소만 콕 집어 물어 사용자를 단답으로 유도했다.
//   "어젯밤 꿈 기억나? 먼저 꿈에서 어디에 있었는지 말해줘 🌙"
//   (게다가 이모지가 있어 시스템 프롬프트의 '이모지 금지'와 모순이었다)
const OPENING_QUESTION =
  "어젯밤 어떤 꿈을 꿨어? 기억나는 대로 편하게 말해줘";
```
사용자가 한 번에 다 쏟아내는 것을 **막는 게 아니라 유도**한다. 그게 이 구조의 최선 경로(1턴 만에 4슬롯 → 2턴째 `complete`)다.

### 강제 종료 안전망 — 최대 5턴
슬롯이 계속 안 채워져도 **5턴째에는 반드시 마무리**한다(무한 되묻기 = 비용·이탈 위험).
서버가 5턴째에 아래를 시스템 프롬프트에 덧붙인다:
```
[중요] 마지막 턴입니다. 남은 슬롯이 있어도 더 묻지 말고,
비어 있는 슬롯은 "기억나지 않음"으로 채운 뒤 complete를 true로 두고
짧고 따뜻하게 마무리하세요.
```

### 하위 호환 — build 8이 스토어에 라이브 ⚠️
`POST /interpret/chat`의 기존 필드(`text` / `nextStep` / `complete`)는 **반드시 유지**한다.
build 8은 `step`을 필수로 보내고 위 3개 필드를 기대하므로, 계약을 깨면 **이미 설치된 앱이 고장난다.**
- 요청의 `step`은 **받되 무시**한다 (진실 소스는 `messages`)
- `nextStep`은 **채워진 슬롯 수 + 1**로 환산해 내려준다 → build 8의 "N/5단계" 표시가 자연스럽게 동작
- `slots`는 **새로 추가되는 필드** — build 8은 모르는 필드라 무시하고, build 9가 진행 표시에 사용
- 덕분에 **서버를 앱보다 먼저 배포해도 안전**하다

### 줄거리 생성 (S-2, `POST /api/dreams/{id}/summary`)

> **2026-08-16 개정.** 이전 초안은 `summary`와 함께 `title`/`tags`/`characters`/`places`도 뽑게 돼 있었으나,
> **`tags`/`characters`/`places`는 현재 쓰는 곳이 없다**(`_to_summary`가 `tags: []` 하드코딩, Archive 백엔드 미구현).
> 안 쓰는 값을 뽑으면 출력 토큰만 낭비이므로 **`summary` 하나만** 뽑는다.
> 인물·장소 추출은 **2-1 Archive 백엔드**에서 이 프롬프트를 확장하며 되살린다.
> `title`도 뺐다 — 이미 `generate_title`이 `thinking_budget=0`으로 따로 돌고 있어 중복이다(§4).

```
다음은 사용자와 나눈 꿈 기록 대화입니다.
이 대화를 바탕으로 꿈 일기를 자연스러운 서술형 한국어로 정리해주세요.

요구사항:
- 1인칭 시점 ("나는 ... 있었다")
- 시제: 과거형
- 대화에서 언급된 장소, 인물, 사건, 감정을 모두 포함
- 언급되지 않은 내용은 추가하거나 상상해서 지어내지 말 것
- 사용자가 "기억나지 않는다"고 한 부분은 굳이 언급하지 말고 자연스럽게 넘길 것
- AI의 질문은 빼고, 사용자가 말한 꿈 내용만으로 구성할 것
- 분량은 대화에 담긴 내용만큼만. 짧은 꿈은 100자 안팎이어도 좋고,
  내용이 많아도 500자 안쪽으로.
  분량을 채우려고 없는 내용을 지어내는 것이 가장 나쁘다.

대화 내역:
{chat_history}

JSON 형식으로 응답:
{
  "summary": "꿈 줄거리 텍스트"
}
```

**⚠️ 분량 요구사항을 "150~300자"로 못박지 말 것 (2026-08-16 실측)**
초안은 `150~300자`였는데 **양방향으로 다 어겼다** — 짧은 꿈은 109자(미달), 긴 꿈은 473자(초과). 출력 길이가 **입력 대화 분량에 그대로 비례**하기 때문이고, 짧은 꿈에서는 `150자 이상`과 `지어내지 말 것`이 **서로 충돌**한다. 모델은 충실성을 택하는데 **그게 올바른 우선순위**다. 그래서 고정 범위 대신 "내용만큼만, 500자 안쪽"으로 바꿨다. 그래도 486자가 나온 사례가 있으니 **상한은 강제가 아니라 유도**로 이해할 것.

### thinking 비활성화 — 실측 근거 (2026-08-16) ⭐

꿈 2건(짧은 것 `raw 65자` / 긴 것 `raw 848자`)으로 세 설정을 비교했다:

| 설정 | thoughts | 길이 | 소요 | 비용 |
|---|---:|---:|---:|---:|
| 기본값 (짧은 꿈) | **1,109** | 131자 | 5.69초 | ₩4.35 |
| `budget=512` (짧은 꿈) | 450 | 140자 | 2.75초 | ₩2.10 |
| **`budget=0`** (짧은 꿈) | **0** | 109자 | **1.27초** | **₩0.40** |
| `budget=512` (긴 꿈) | 372 | 393자 | 4.19초 | ₩2.60 |
| **`budget=0`** (긴 꿈) | **0** | 473자 | **2.46초** | **₩1.50** |

- 기본값은 `thoughts 1,109` vs `output 79` — **실제 출력의 14배를 추론에 썼고 그 호출 비용의 89%**. 제목 생성에서 발견한 것(`thoughts 866 / output 7`)과 같은 패턴 (`IMPROVEMENTS.md` 1-1b)
- **세 설정 모두 장소·인물·사건·감정을 빠짐없이 담았고 1인칭·과거형도 지켰다.** 품질 차이가 미미한데 비용은 2~10배, 속도는 1.7~4.5배 차이
- 오히려 `budget=0`이 더 충실한 사례도 있었다 — 사용자의 "꿈에서 깼을 때는 아니었지만"이라는 단서를 기본값 버전은 빠뜨렸는데 `budget=0`은 살렸다
- → **`thinking_budget=0` 확정.** 줄거리는 "대화에 이미 있는 내용의 재구성"이라 추론이 기여할 여지가 작다. **해몽은 유지** — 거기선 thinking이 실제로 일한다(1-1c)

**운영 메모**
- `_log_usage`에 `call=summary`로 기록 → 배포 후 실사용 단가를 계속 추적
- **실단가 ₩0.4~1.5** (입력 분량 비례). 꿈 1건 ₩14.4 기준 **약 +7%**. thinking을 켠 채였다면 +30%였다
- **멱등**: `dreams.summary`가 이미 있으면 Gemini를 부르지 않고 기존 값을 반환한다. 이것이 사실상의 비용 상한이라 별도 사용량 한도를 두지 않는다

## 2. AI 해몽 해석

### 시스템 프롬프트
```
당신은 꿈 해석 전문가입니다.
한국의 전통 해몽 + 융(Jung) 심리학 + 현대 심리치료의 관점을 융합하여 해석해주세요.

해석 원칙:
- 단정적이거나 불안을 조장하는 해석을 하지 마세요.
- 부정적인 꿈도 성장과 내면 탐구의 신호로 긍정적으로 해석하세요.
- 전문 용어를 최대한 쉽게 풀어서 설명하세요.
- 사용자에게 "당신"이라고 직접 말하는 따뜻한 2인칭 톤으로 작성하세요.

언어: 한국어
```

## 4. 꿈 제목 자동 생성

### 프롬프트
```
다음 꿈 내용에 어울리는 시적이고 감성적인 제목을 만들어주세요.

조건:
- 10자 이내
- 한국어
- 꿈의 핵심 이미지나 감정을 담을 것
- 일기 제목처럼 서정적으로

꿈 내용: {dreamContent}

JSON: { "title": "제목" }
```

## 5. 에러 처리 및 폴백

### AI 응답 실패 시
```javascript
const FALLBACK_MESSAGES = {
  chatError: "잠깐 꿈나라로 다녀왔나봐요 🌙 다시 한번 말해줄래요?",
  interpretError: "지금 꿈을 해석하는 데 시간이 좀 걸리고 있어요. 잠시 후 다시 시도해주세요 ✨",
  illustrationError: "그림을 그리다가 잠이 들었나봐요 😴 나중에 다시 시도해볼게요"
}
```

### 토큰 절약 전략
- 대화형 기록: 최근 10턴만 컨텍스트에 포함 (오래된 내용 요약 후 압축)
- 해몽: 꿈 요약본(rawContent)만 전달, chatHistory 전체 전달 금지
- 일러스트: 프롬프트 생성 + 이미지 생성 2단계로 분리 (에러 재시도 효율화)
